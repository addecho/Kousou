技术基线已重新设计，详见 [架构决策](architecture.md)：模块化单体、四包工程、方案聚合存储、浏览器搜索及服务端快照复核。本文的产品范围及验收要求与该架构配套使用。

## 1. 产品目标与版本边界

做一个独立、自托管的购物决策工作台：用户录入想买的商品、可选凑单商品和优惠条件，理解每笔钱如何计算，再比较不同购买方案。首要问题是“买齐这些东西，总共需要付多少、额外买了什么、结果有多少不确定性”。

保留原目标：手动录入优先、同账号多店结算、可解释优惠计算、人工校准、匿名恢复 Key、PostgreSQL 持久化。**当前默认先做淘宝/天猫工作流并完整跑通；京东后置。** 不接管商城登录、购物车或下单。

用户已明确：未来多平台就是同时打开两个独立页面，由用户比较。当前不建设双面板比较器、同款匹配、跨平台需求分配或联合优化；这些也不作为 V1.1 承诺。只保留 platform 字段和规则模块边界，避免提前搭建复杂框架。

| 阶段 | 必须交付 | 后续扩展 |
|---|---|---|
| V1 核心 | 淘宝/天猫单平台；每方案一个账号、一次结算、多店多 SKU；券及资产录入；金额账本；保存、校准、凑单搜索 | 不承诺覆盖全部活动 |
| V1 可选导入 | 单图上传、人工核对导入；OCR 插拔且不阻塞手工流程 | 多图解析和外部 OCR 异步队列 |
| 后续平台 | 核心跑通后增加京东独立规则与页面；可同时打开两个浏览器页面 | 各页面独立选择账号与方案，由用户比较 |
| 后续 | 新平台规则、历史价格、退货影响分析、预售/国补专门模块 | 每项都要独立来源、模型和测试 |

国补、以旧换新、定金预售、跨境税费、后返权益暂只记录。缺少这些金额时输出“不完整”，不能静默当零。凑单默认保留所购物品；不以买后退货作为节省前提。

## 2. 审查结论与必须修正处

| 原计划问题 | 修订决定 |
|---|---|
| 多平台设想容易扩大首版范围 | 当前方案固定平台和账号，一个方案一次结算；多平台以后独立页面使用 |
| after_item/after_shop 无法表达指定类型优惠扣除 | 以不可变价格账本和有限BasisSpec定义门槛；保留平台原生价格字段 |
| 同店被直接视为同子订单 | 店铺、促销判定组、平台订单组、运费组分开；合并规则由适配器提供 |
| 自动择优可能误成全局任意选券 | 区分平台强制择优、用户可选与实验覆写；优化器只搜索真实可选空间 |
| 所有分摊均用最大余数法 | 作为内部模拟默认；有官方算法才标为平台分摊，否则逐行价格只是估计 |
| 模拟保存可能误扣券资产 | 替代方案独立模拟，保存不扣减真实余额；同一结算内限制券次数 |
| 按优惠面额或现金排序会误导 | 同需求覆盖、含运费、资产消耗单列；比较基线显式固定 |
| 先完成大量 CRUD 再验证算法 | 先建立规则证据和纯引擎数值用例，再做端到端最小工作流 |

## 3. 公开规则如何落实

### 淘宝/天猫

TB-01 公告要求店铺券、多件优惠及第三方店铺满减满折在同子订单互斥择优，示例 2×100、九折与 200-10 得 180。公告排除飞猪，且升级时间附调整可能，预设需保存这一边界。其他层级不受本次变更不等于任何层级都可任意叠加。

TB-02 是服饰行业特定活动合同：门槛聚合符合活动资格的商品，剔除非商品收费，扣除单品宝而不扣店铺优惠和单品直降；与平台购物券冲突。不能把它压缩成一个通用 after_item，也不能自动用于所有品类券。档位、活动期与具体商品资格仍需券面/活动通知确认。

TB-03 说明商家签约、商品报名审核和参加活动是不同状态。商品处于某类目不是参与活动的充分条件。商家软件服务费是商家成本，不加入消费者价格；报名活动互斥不直接转为消费者券冲突。

### 京东（研究储备，不属于 V1 实现或发布门槛）

JD-01 的普通东券按适用商品的京东价总额判断门槛，同商品普通店铺/品类/全品类东券互斥；不重叠商品可分别用券。保留 jd_price，不默认为前一阶段折后价。全品类券每订单最多一张，需要明确订单作用域。PLUS 等例外必须有对应具体规则才启用。

JD-02 的 200+300 商品算例应得 475，作为官方数值 fixture。渠道和区域是使用条件，不另造优惠层级。商品券不抵运费，全球购不直接套普通预设。

JD-03 运费文有旧日期和多张叠加描述，按待核验候选保留。运费优惠另建规则，不能复用普通商品券“一张”的限制，也不能默认所有运费券都叠加。

每个模板必须有平台、活动、适用区间、证据、未知条件、版本及测试。未经确认的模板不进入“已确认条件下”的默认报价。

## 4. 核心领域结构

```text
Workspace
  PlatformAccount                       逻辑账号，不含商城登录凭据
  Shop / Offer / OfferObservation        店铺、SKU报价及观察版本
  PromotionRule / CouponAsset            规则定义与账号持有实例
  CheckoutPlan                          固定平台、账号、时点和渠道的一次结算
    PlanLine                            报价、数量、必买/可选/凑单角色
    PromotionGroup / OrderGroup         优惠判定组与平台订单组
    ShippingGroup                       配送及运费计算组
    Overrides / CalculationSnapshot     人工修正与历史
```

一个 CheckoutPlan 对应一次结算，可以包含多个店铺。多个保存方案是替代模拟，不同时扣减资产。当前不做多批次执行编排；以后确有需求再引入上层组合对象。

Shop 以 workspace/platform/externalShopId 标识，不依赖消费者账号。Offer 是店铺 SKU 报价，不等于标准商品；账号专享价在 OfferObservation 中绑定 accountContext。平台、地区、渠道、时点不同的报价不可悄悄复用。

商品记录品牌/型号、规格、包装数量和计量单位供用户判断；当前不建标准品匹配库和跨平台等价关系。

同 SKU 多件参与不同优惠时保留数量切片及稳定 sliceId，禁止一件货重复占券资格。产品内部组 ID 不宣称等于真实平台子订单 ID。

## 5. 规则协议与价格账本

### 输入与版本

统一 PricingInput 包含 schemaVersion、engineVersion、rulesetVersions、valuationTime、timezone、currency=CNY、accountContext、lines、groups、rules、assets、shipping、overrides。使用 Asia/Shanghai 解释活动时间，存 UTC 时间戳并保留原时区；有效期约定左闭右开，来源“截至某日”由模板转换。

金额用整数分，内部 bigint；关系型金额字段用 BIGINT，JSON 内用十进制字符串。折扣用整数分子/分母，明确在哪一步取整，不另引入 Decimal 系统。所有输入有数量、金额、规则数及文档体积上限，禁止负数量、循环依赖和未知规则类型。

每条规则包含：

- identity：ruleId、version、platform、activityId、sourceRefs。
- eligibility：账号、SKU、类目、已确认报名、会员、渠道、地区、时段；返回 eligible/ineligible/unknown 及依据。
- thresholdScope 与 benefitScope：分别定义参与门槛和获得优惠的数量切片。
- thresholdBasis 与 discountBasis：有限BasisSpec选择命名价格基数及排除的账目类型，不能执行用户 JavaScript。
- benefit：固定减、比例折扣、每满、阶梯、多件、封顶；次数与取整粒度明确。
- stacking：冲突组、作用域、每行/订单/批次上限、商品不重叠条件。
- selectionPolicy：platform_best、user_selectable、mandatory；未知平台行为不得默认为自由选择。
- allocationPolicy：算法、权重、上限、舍入和是否与平台一致已验证。
- validity 与 evidence：生效范围、证据和未确认条件。

首版采用有限BasisSpec，例如 priceBasis + excludedAdjustmentKinds，不开放通用AST或自定义公式。TB-02 模板使用确认后的合同商品基数减 single_item_bao；不把所有商品级折扣一起减去。原始报价若已含某优惠，entry 标记 includedInQuotedPrice，禁止再次扣减。无法还原所需原始基数时返回 unknown_basis。模板阶段依赖在代码中校验，用户只选择受支持策略。

### 引擎流程

1. 校验版本、上下文、数量切片及分组，冻结输入。
2. 生成原价、活动报价、平台价格等基数；未知的字段保持未知。
3. 解析资格与依赖图，拒绝循环/不完整依赖；选择合法组合。
4. 按规则各自门槛、折扣基数和互斥作用域执行；不靠 priority 猜业务顺序。
5. 创建逐笔优惠账目，按受益范围分摊；分摊不得超过剩余可抵金额，溢出重新分配或截断并解释。
6. 计算各运费组的基础费用、包邮门槛和运费券，再按策略处理资产与支付优惠。运费门槛也有独立口径。
7. 校验本次结算的券次数、余额与额度，汇总方案。
8. 输出 trace、被拒原因、未知条件、版本、输入摘要及三类金额。

固定金额默认使用最大余数法，余数相同按稳定 sliceId 排序。此规则保证内部守恒，但不能据此保证退款分摊与平台一致。退款不使用简单“按当前折后价退回”的推断。

输出金额分为商品/运费促销后应付、账户资产抵扣、新增现金支付；红包、预付购物金、积分分别显示。返券返豆不减本次现金。人工补偿独立账目，不修改算法原始结果。

计算可信度与优化状态是两个字段：certainty=confirmed_inputs/assumption_based/incomplete；searchStatus=optimal_within_enumerated_domain/best_found/infeasible/not_run。confirmed_inputs 也只指模型输入已确认，不保证平台结算一致。缺失运费/资格时不能把部分金额标成完整总价。

## 6. 单平台凑单优化

### 比较口径

优化前冻结购物车版本、必买商品及数量、账号、地址/渠道与观察时点。结果显示必买商品覆盖、额外商品、商品应付、运费、资产消耗、现金及未知项。未买齐必买商品的候选不是可行解。结果列表比较本次搜索的同平台候选，不建立独立的跨平台比较模块。

基线是满足同需求且不增加凑单品的合法方案，使用同一资产策略和价格观察。无可行基线时不显示净节省。净现金节省 = 基线现金 - 候选现金；“优惠更多”与“花钱更少”分别显示。若资产消耗不同，先并列显示；只有用户明确给出资产估值才显示折算总成本，不自行给积分/购物金设兑换价值。

### 搜索职责

V1 在一个批次内搜索已录入商品数量、用户可选券及允许的组合。输入含必买、可选、凑单角色、预算、额外件数/金额上限、库存、锁定项；仅比较优惠面额不是目标函数。

先求不加凑单品的基线，再搜索候选。建议初始限制 20 种候选 SKU、每种最多 3 件、3 秒预算；这是保护限制，不是性能承诺。不能在优惠非单调时假设加商品只会增加应付；只能用证明安全的下界剪枝。

通过同一core定价模块复核完整结果，缓存键包含规则版本、资格、上下文、资产与 override。最多返回 5 个按规范化购买组合去重的可行方案，不凑满数量。超时保留基线/当前可行解，显示搜索范围与未证最优；浏览器Web Worker运行并可取消，关页停止，首版不建立服务端优化任务队列。选中结果写回草稿，保存快照时服务端重新计算。

增加第二个平台时复用计算接口，提供对应规则和独立页面。跨平台自动分配及联合搜索不在本计划范围内。

## 7. 界面与工作流

当前只实现一个平台工作台。未来通过打开两个浏览器标签页或窗口分别操作不同平台，不做内置双面板。

单方案编辑采用商品清单、结算解释、券中心。顶部选择账号与方案，当前平台明确显示。商品按店铺分组，优惠组和运费组可查看，编辑不要求用户理解数据库术语。

桌面采用三栏，窄屏改商品/结算/券中心标签；高级编辑用抽屉。方案 ID 放在页面路由中，各标签页独立持有选中状态，不能把“当前方案”存成全局共享 localStorage 状态。两个页面编辑不同方案互不串单；编辑同一方案通过 revision 检测冲突。历史快照不会因另一页面改券而变化。

券录入保留快捷模式：券种、面额/门槛、适用商品、领取/期限。平台模板填充的是候选条件；高级抽屉允许修改门槛口径、冲突、数量与来源。展示已应用、差门槛、冲突、未领取、过期、待核实及实际参与商品。

单图识别先保存私有临时附件与候选结果，人工确认后才生成生效规则/券资产；这修正旧稿“未确认不得持久化”的歧义。未配置 OCR 时直接手工填写；批量导入后置。自动保存用 revision 和请求序号，失败/冲突不能显示已保存。

## 8. 技术结构与依赖方向

采用 Vue 3、TypeScript、Vite、Vue Router、Naive UI；Vue composable 管草稿，TanStack Vue Query 管服务端缓存，首版不引入Pinia。Fastify + Zod 提供同源API及构建后的SPA；postgres.js + Drizzle访问PG；Vitest + fast-check + Playwright覆盖验证。PG18 当前核实小版本为18.6，实施时验证镜像并锁定digest。取舍及执行细节见[架构决策](architecture.md)。

```text
apps/web/src/                     功能页面、草稿、API缓存、Web Worker
apps/server/src/modules/          会话、方案、商品、券、导入用例
apps/server/src/db/               Drizzle schema/migrations
packages/core/src/                类型、金额、资格、定价、分摊、trace、优化器
packages/core/src/policies/taobao/ 平台预设与确定性策略
packages/contracts/src/           Zod请求响应、版本和序列化协议
tests/fixtures/{synthetic,taobao}/
tests/{integration,e2e}/
code/research/
compose.yaml
docker/
```

工程只建web、server、core、contracts四包。core不依赖UI/DB/网络；contracts依赖core类型；web和server依赖两者，彼此不导入。优化器调用同一定价模块。服务端读取指定方案修订，重新计算并原子写入快照，不信任客户端金额。引擎不得读取当前时间、随机数、进程环境或远程服务，所需上下文全部显式输入。浏览器与服务端引擎版本不兼容时保留草稿并提示更新。

## 9. 数据与接口

| 数据表 | 核心约束 |
|---|---|
| workspaces/workspace_keys/sessions | 恢复密钥摘要、设备会话与撤销记录 |
| platform_accounts/shops | 逻辑账号；店铺不依附购买账号 |
| offers | 手动SKU、规格、当前报价、观察时间与账号上下文 |
| checkout_plans | 平台、账号、revision、schema_version及document JSONB；行、分组、规则副本、资产预算和覆写在文档内 |
| coupon_assets | 账号持有实例、规则文档、有效期、次数和revision |
| calculation_snapshots | 不可变完整输入、结果、引擎/规则版本、输入摘要 |
| checkout_observations | 真实结算观察、差额说明、附件引用 |
| attachments | 私有文件、临时/已关联状态、过期时间 |

所有业务行明确workspace_id；关系列使用同租户复合外键，JSONB引用由服务端限定租户/账号查询并校验，不能依靠JSONB外键。常查字段单独索引，方案文档经Zod和领域约束校验并限制体积。官方模板及证据随代码版本管理；方案保存报价和券规则副本，源数据修改不自动改变方案，显式刷新才更新。历史快照冻结输入，保存模拟方案永不扣减资产。逻辑领域对象不要求各对应一张表。

API 保留旧稿会话、商品、规则、附件接口，并以 /api/v1 增加：

- GET/POST /plans；GET/PUT /plans/:id：以整份方案为保存单位，PUT携带expectedRevision。
- POST /pricing/calculate：无副作用的模拟，返回 inputRevision/hash。
- 凑单搜索通过浏览器Worker消息协议执行，不设服务端任务API。
- POST /plans/:id/snapshots、/overrides、/observations：冻结与校准。
- /health/live、/health/ready：进程状态与数据库/迁移就绪。

所有写入验证租户；用条件UPDATE原子比较并递增revision，冲突返回409；同一页面的自动保存请求串行并合并待发送编辑。快照保存和确认导入支持幂等键。API缓存不覆盖未保存草稿。快照存输入、结果、规则及引擎版本；引擎升级重新模拟生成新快照，不覆盖旧结果。

## 10. 安全、部署与运维

恢复 Key 用至少 128 位安全随机数，仅首次展示；服务端带 pepper 的 HMAC 摘要。设备会话令牌随机生成，只存摘要，生产 Cookie 使用 Secure/HttpOnly/SameSite；恢复、轮换、撤销、限流、CSRF/Origin 检查和租户越权测试都属于 V1。

不存商城 Cookie、密码或支付凭据。图片验证实际类型及像素上限，私有存储、鉴权读取、清理临时文件；外部 OCR 明确告知外传。V1 商品链接不自动抓取，避免任意 URL 服务端请求；后续抓取必须单独设计 SSRF 防护。

Compose核心为app和db，公网部署增加Caddy处理HTTPS。app由Fastify同时提供SPA与API，前后端一次发布；开发时Vite代理API。数据库不映射公网。PG18数据卷按官方镜像要求挂载/var/lib/postgresql，实施时复核。依赖冻结安装；凭据通过环境提供，.env.example只放占位说明。

迁移作为单次部署步骤，readiness检查schema版本。首版无Redis和持久任务队列。浏览器Worker承担短时搜索；可选OCR优先受限同步请求，超时回退人工。仅当供应商要求异步或批量导入需要断线续作时再引入成熟PG任务库及worker。服务端普通定价有复杂度上限，实测若阻塞事件循环则移入有界Node Worker池。

每日数据库备份和独立附件备份，记录一致性时间点；恢复演练验证方案、规则、图片和设备恢复。pepper 需独立安全保管，缺失会影响恢复 Key 校验。主要版本升级采用官方迁移方法；导出/导入有版本与校验，不包含服务端秘密。
