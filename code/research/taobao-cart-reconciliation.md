# 淘宝真实购物车逐层对账

录入日期：2026-10-22。证据：用户本轮上传的8张截图，编号按上传顺序。截图仅显示时间，没有日期，不推断活动年份。性质是购物车预估，不是提交订单页或支付凭证。

本轮完成金额核对、结构差距审查和证据回归测试。尚未验证完整规则，不修改生产计算引擎，不把手填优惠金额包装成算法验证通过。金额样本见 `tests/fixtures/taobao-cart-observation.ts`。

## 1. 已确认的三件商品总账

| 商品 | 划线原价 | 平台加补后显示金额 | 差额 |
|---|---:|---:|---:|
| 饮料 | 59.90 | 36.70 | 23.20 |
| 袜子 | 59.00 | 49.87 | 9.13 |
| 洗衣机 | 3020.00 | 1976.45 | 1043.55 |
| 合计 | 3138.90 | 2063.02 | 1075.88 |

店铺优惠：官方立减461.90 + 直降20.00 + 单品直降359.35 = 841.25。

平台优惠：88VIP 2.00 + 淘金币81.63 + 红包150.00 + 首单礼金1.00 = 234.63。

总账：3138.90 - 841.25 - 234.63 = 2063.02。分类父项不能与其子项重复抵扣。红包明细中的家电数码消费券150元是同一笔优惠，不再另扣150元。

截图显示袜子官方立减8.90、淘金币0.23，恰好得到49.87。洗衣机官方立减453.00、限时补贴359.35已显示；按该归属反推剩余优惠231.20。若150元红包全部用于洗衣机、且其余优惠无其他分摊，则洗衣机淘金币为81.20，饮料淘金币为0.20。这个分摊是假设，不存作已确认规则。

## 2. 可推导但仍须确认的计价基数

### 家电数码消费券

三档券得到一致的累计值：

- 3000 - 873.55 = 2126.45。
- 5000 - 2873.55 = 2126.45。
- 8000 - 5873.55 = 2126.45。

2126.45 = 洗衣机显示价1976.45 + 已抵150。支持“按符合范围商品的某个券前净额计门槛”的假设，而不是整车原价3138.90或整车应付2063.02。仍需核实150券的门槛、适用SKU、互斥关系，以及淘金币等是否影响门槛。

“再买873.55”不等于随便加入标价873.55的商品就能达标。新增商品必须符合该券范围，而且其自身优惠可能降低门槛贡献。

### 88VIP与首单礼金

88VIP展开显示“小计3138.90，减2.00”，不能据此把整车3138.90都乘以5%。饮料直降后39.90乘5%为1.995，若按分四舍五入可得到2.00，但截图尚不足以证明受益范围、折扣基数和取整顺序。首单礼金明确关联饮料，减1.00。

### 运费与政府补贴

天猫超市提示88包邮、还差48.30，反推包邮累计39.70。这既不是饮料显示价36.70，也不是直降后39.90；运费门槛需要独立基数、商品范围及重量条件，不能直接使用最终商品实付。截图未给出实际运费，不将未知运费设成已确认零元。

政府补贴后约1679.98属于另一个待领取/核验场景，没有进入当前2063.02总账。1976.45乘85%约为1679.98只能形成15%的候选解释，不能证明资格、封顶或最终扣减基数。

后续实施更新：用户要求采用分类比例预设并手动调整，已按 [简化国补设计](government-subsidy-model.md)接入引擎0.2.0。用户明确启用后的手动模拟可参与试算与凑单，但不代表平台已确认补贴资格；未启用时不抵扣。

## 3. 四件与三件场景不可混用

四件合计2395.87、优惠1161.03；三件合计2063.02、优惠1075.88。差额为应付332.85、优惠85.15。若其他输入和展示口径未变，原价差额推算418.00，但第四件未完整展示。不能据此认定第四件独立到手价332.85，也不能认定其他三件的优惠完全未变化。

## 4. 当前模型的必改点与设计边界

当前代码位置：`packages/core/src/index.ts` 的 Rule、scoped、inspect、店铺择优和运费计算。

| 当前结构 | 本样本揭示的问题 | 下一版要求 |
|---|---|---|
| 商品只有一个 directOff | 洗衣机官方立减与限时补贴同时存在，合并虽能对金额但失去来源与门槛语义 | 商品级优惠明细列表，保留类型、金额/公式、顺序、证据 |
| 每店所有 shop 规则只择一个 | 展示归类“店铺优惠”不代表所有子项互斥 | 展示分类与执行阶段分开；仅在明确互斥组内择优，不直接取消现有店铺券互斥 |
| 四种全局 basis | 消费券、折扣、包邮各有独立基数 | 有类型的阶段金额账本；门槛基数与折扣基数分开，支持受控扣除项 |
| 商品全局 eligibility | 同一商品可参加一种活动，却不能用88VIP消费券 | 按规则/活动与商品记录 confirmed / excluded / unknown |
| 空 lineIds 代表全范围 | 未绑定预设容易被解释为整车适用 | 显式 unbound / all_in_scope / explicit_lines，未绑定不得应用 |
| 平台优惠按数组顺序、金额按余额比例分摊 | UI列出的顺序与小计不证明执行顺序，真实逐商品优惠未必按比例 | 明确阶段依赖、受益范围、取整单位和分摊方式；未知时不生成伪精确逐行结果 |
| 资产抵扣一个总数 | 淘金币、消费券、礼金有不同SKU资格和门槛影响 | 分项资产/优惠实例，禁止重复录入同一笔抵扣 |
| 包邮直接使用最终商品金额 | 本例包邮累计39.70不同于显示价36.70 | 独立运费策略、基数、重量约束，未知单列 |

规则中心应管理版本化预设、证据、适用期和支持能力，不保存“用户已领取”或当前方案SKU绑定。模板版本、账号持有实例、方案绑定分离；已发布定义不可原地覆盖，旧方案保留解析后的规则副本。新增算法仍需引擎发布，不用任意JavaScript公式执行或人工校准掩盖缺失语义。

## 5. 接下来的逐层验收

1. 获取单商品优惠展开、消费券完整规则；只勾选洗衣机，核对淘金币、红包与门槛差额。
2. 确认饮料VIP、首单礼金、淘金币和包邮基数；获取提交订单预览中的运费，不要求实际支付。
3. 按证据实现V2明细账本和规则作用域，显式迁移V1，不静默改变旧方案含义。
4. 先使单商品及三商品样本的每个已知层级通过引擎测试，再测门槛前后1分钱、适用/不适用SKU、券互斥和阶段顺序。
5. 补齐第四件后验证选中变化引起的重新定价；政府补贴独立情景验收。

当前测试仅证明截图金额转录自洽，不代表现有 calculate() 已支持这组真实订单。暂不将此样本加入“可用于凑单优化”的正式预设。
